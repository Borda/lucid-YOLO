## WP-183 — the box terms scored densely, so the step traces as one graph

<a id="wp-183"></a>

**A boolean gather is a shape the compiler cannot know.** `pred_boxes[fg_mask]` lowers to `aten.nonzero`, whose output length is a property of the data, and `torch.compile` answers that with a graph break; the detection step carried seven of them, at the masked gathers. Recorded 2026-09-18. The replacement evaluates every term over the full `(B, A)` anchor grid — CIoU through a `reshape(-1, 4)` since its contract is two-dimensional, ProbIoU directly since it broadcasts, the L1 differences against the dense stride, the angle term over the whole branch — and selects the positives afterwards. The selection is a `torch.where`, not a multiply by the mask: a background anchor's target is the all-zero box, so the dense CIoU there is scored on a degenerate pair, and `0 * NaN` is still `NaN` where `where` is an exact selection in both the value and the backward pass. What remains is a dense sum in which every off-positive term is an exact zero, and `square_angle_loss` already documents whole-branch input with `q_i = 0` background as its intended second use.

**Loss-identical, measured rather than argued.** On a COCO batch the two forms differ by an absolute `0.0` on every term, the gradients stay finite on an image with no positives, and the pre-change CPU step snapshot holds at its existing tolerance; in eager the step is 2% faster, with the seven `nonzero` calls gone. The masked implementation is kept verbatim as a private oracle in each test module, and the dense form is held against it on random assignments — an image with no positives, an all-background batch, and degenerate predictions (zero-area, inverted, all-zero, both sides collapsed) planted on background anchors — to `1e-6` on values and gradients. The oriented oracle draws `gt_index` from `[0, N)` with `N ≥ 2`, so the gather over the padded instance axis is exercised on every column rather than only its first. WP-184 is what the one-graph step is for.

**What the accelerator gate said afterwards (2026-09-19).** On an A100-40GB, two of the five `goldens/gpu/` rows moved out of band under this change alone: keypoints `0.5696 → 0.4919` and oriented `0.9783 → 0.9088`, per-commit on the same machine, with WP-182's layout change accounting for `−0.021 / −0.040` of the path and detection, segmentation and `shapes_regression_det` holding. The arithmetic is the same; the summation order is not, and the overfit gate is a 100-epoch trajectory that amplifies a `1e-7` per-step difference into a different endpoint — the same sensitivity the [WP-177](https://borda.github.io/lucid-YOLO/work_packages/wp-177/) escalation measured across seeds on unchanged code. The principal resealed both rows at the measured values (ESCALATION 2026-09-19, WP-186); the oriented band is now `clamped_tolerance`-narrow at `± 0.0088`.

**And what three seeds said (2026-09-20).** The control the escalation asked for, run per commit on the same A100: the oriented move that looked monotone at HEAD splits into WP-182's `−0.020` (3 of 3 seeds down) and this change's `−0.014` (2 of 3), and keypoints span `0.49`–`0.73` across nine runs of the same objective. A layout change with no arithmetic in it producing the same signature as the loss rewrite is the evidence that the signature is the gate's, not the change's. Full table in ESCALATION 2026-09-19's follow-up.



## WP-188 — notebooks as sources, the `.ipynb` as a build product

<a id="wp-188"></a>

**The format question was decided by what the gate can read.** Recorded 2026-09-21. A notebook is worth publishing only while it still runs, and nothing about publishing one checks that; so the first decision was that every notebook is a `.py` the existing machinery already handles -- ruff lints it, `license-headers` scopes it, and `tests/notebooks/test_notebooks_run.py` runs it as a script under `LUCID_NOTEBOOK_FAST=1` on every `make gate`. Jupytext's percent format is the one that costs nothing: a `# %%` line is a comment to Python and a cell to the converter. The `.ipynb` follows from the `.py` at build time in two places, `docs/notebooks/` for the site and `notebooks/<name>.ipynb` on `gh-pages` for the Colab badge, and neither is ever committed to `main`; `no-ipynb-tracked` reads the index on every commit because `.gitignore` is advice and `git add -f` ignores it (D25). The script run ruled out one thing: the Colab bootstrap could not be a `!git clone` line, because jupytext writes a magic into the `.py` as a comment and a guarded block of comments alone is a `SyntaxError` when the file runs as a script -- so the bootstrap, and after it every console command the demo notebooks ran, went through `subprocess`.

**The script run is withdrawn; the gate executes the notebook through a kernel.** Revised 2026-09-21, once the four demo notebooks existed. Each of them is a sequence of console commands -- `lucid-data download`, `lucid-yolo fit`, `lucid-eval`, `lucid-predict` -- and as `subprocess.run([...])` lists they read as argv arrays, not as the command lines `docs/TRAINING.md` spells. The user's ask was that they read as plain shell, and that decides the gate's mechanism rather than the other way round: each command is a `%%bash` cell -- `# %% language="bash"` in the `.py` with the script commented beneath, comments to a script run -- so the proof moves from "run the `.py`" to "convert the `.py` and execute the `.ipynb` with a kernel". The test now runs `jupytext --from py:percent --to ipynb --execute --set-kernel python3 --run-path <repo root>` per source, the same conversion `make notebooks` makes plus execution, and the `subprocess` reasoning above no longer applies because nothing runs the file as a script any more; the bootstrap is `!git clone` and `%pip install -e lucid-YOLO` under the same `google.colab` guard, with `os.chdir` and the `sys.path` insert keeping the block a block. Values cross into a shell cell through the environment -- the Python cell above does `os.environ.update(DATA_ROOT=..., FIT_ARGS=...)`, the fast budget being one such string of flags -- and a switch the shell itself has to make reads `$LUCID_NOTEBOOK_FAST`, so the download the fast run skips and the `lucid-predict` loop only the fast run makes are `if` blocks in bash beside the command they guard. Three things were measured rather than assumed. A `!` line does not fail the notebook -- `!false` followed by a `print` printed, under `nbclient`, with the cell green, IPython storing the status in `_exit_code` and continuing -- which is why the commands are `%%bash` cells and not `!` lines: the script magic raises `CalledProcessError` on the cell's exit status and nbclient stops, as a probe with `false` confirmed; that status is the last command's, so a cell with more than one opens with `set -e`. `--set-kernel -`, jupytext's spelling for "the current interpreter", raises `No kernel found that matches the current python executable`: the kernelspec `ipykernel`'s wheel installs into `.venv/share/jupyter/kernels/python3` has `argv[0]` equal to the bare word `python`, and jupytext compares that to `sys.executable` with `os.path.samefile`. `--set-kernel python3` names that spec directly, and `jupyter_client.manager.KernelManager.format_kernel_cmd` swaps a bare `python` for the launcher's `sys.executable` -- the venv's, since pytest runs jupytext as `python -m jupytext` -- which a probe confirmed from inside the kernel; so there is no `ipykernel install` step, and the test sets `JUPYTER_PATH` to the venv's `share/jupyter` so a user-level `python3` spec, which the search order otherwise puts first, cannot take the name. And `--from py:percent` is not optional: jupytext's `guess_format` counts an *indented* `    # !git clone` -- the Colab block's -- as an unescaped magic, because its escaped-magic test is `not line.startswith("#")` with no `lstrip`, and guesses `hydrogen`, a format that leaves every `# !` line a comment. A jupytext header after the SPDX line and a `[tool.jupytext]` table in `pyproject.toml` were both tried and neither reaches the CLI reader, so the flag went into the test, the `Makefile` and `docs.yml` together; without it the published `.ipynb` would carry `# !git clone` as a comment and the badge would open a notebook that clones nothing. The `dev` group gains `jupytext`, `nbconvert` and `ipykernel` -- `nbconvert` and not `nbclient`, because `jupytext --execute` imports `nbconvert.preprocessors.ExecutePreprocessor` and declares neither as a hard requirement -- and the licence audit on the dev environment stayed clean at 152 distributions. Under `LUCID_NOTEBOOK_FAST=1` the five sources take 18–32 s each through the kernel on an Apple-silicon CPU (the four-task wiring gate the 32 s), kernel start included, against the test's 60 s ceiling, which therefore did not move. The full runs' paths were settled at the same time: a dataset goes under the gitignored `data/` of the checkout -- `data/coco2017` for the three COCO demos, `data/dota` and `data/dota_tiles` for the oriented one -- and the run under `results/demo_<task>`, the Colab detect demo keeping its Drive guidance; the fast run keeps its temporary directory.

**The demos moved off the shell cells; the kernel run stays.** Revised again 2026-09-21, once the four demos were rewritten onto the library: every step is now a call on an object the kernel holds -- `download_coco`, `DetectionLitModule` and `DetectionDataModule` built from the tier's YAML values, `Trainer.fit` and `Trainer.validate`, `lucid_yolo.predict` and `lucid_yolo._viz` -- and the console command is quoted as prose, never run, so the `%%bash` cells, the `os.environ` hand-off and the `$LUCID_NOTEBOOK_FAST` test in bash are gone from them. The three measurements above still stand as measurements, they just no longer bear on the demos. What keeps the gate on `jupytext --execute` through a kernel rather than a script run is the bootstrap: `!git clone` and `%pip install -e lucid-YOLO` are magics, written into the `.py` as comments, and a script run would read them as comments and prove nothing about the two lines a Colab reader depends on; the `--from py:percent` reasoning is theirs as well. One consequence for a figure cell: its last expression is `None if FAST else prediction_grid(640)`, because a bare name as the cell's last line is `B018` to ruff and a call is not. Measured on an Apple-silicon CPU, the four demos take about 11 s each under the fast contract, against 18-32 s through the console scripts. The gate notebook went the other way for the same reason, one file later: the four overfit commands and the shapes regression are development tooling with no library entry point, so `notebooks/development_gates.py` runs them as the `!` lines TRAINING.md spells, `$PROBE` appended under the fast contract -- `--epochs 1 --batches 4`, a probe override the overfit script gained on the shapes script's model, reporting PROBE with the score and enforcing no floor; 26 s for all five commands.

## WP-189 — the drawing code moves into the package, and the dependency it already had is declared

<a id="wp-189"></a>

**Four notebooks would have carried four copies.** Recorded 2026-09-21. [WP-188](https://borda.github.io/lucid-YOLO/work_packages/wp-188/) made `notebooks/*.py` gate-run sources, and the first four notebooks each want two figures: a run's curves and a checkpoint's predictions over a few images, labels beside them. Both existed — `scripts/plot_training.py` drew the first and `scripts/draw_predictions.py` the second — and a notebook cannot import a script, so each notebook would have re-spelled the drawers inline. That is the failure the [WP-067](https://borda.github.io/lucid-YOLO/work_packages/wp-067/#wp-067) entry names from the other direction: a notebook nothing tests rots, and drawing code copied into four of them rots four ways at once, each copy free to draw the rotated box as its envelope again. So the functional core of both scripts moved to `src/lucid_yolo/_viz/` — `curves.py` for the panels and the CSV reader, `overlay.py` for the four per-task drawers, the renderer table and the checkpoint-to-axes path — and each script is now its argument parse, its backend selection and its write. The notebook entry points are two: `plot_curves(metrics)` returns the report's figure titled by the run directory, and `show_predictions(checkpoint, images, annotations)` loads the checkpoint once, draws one panel per image, and lays the labels under the predictions when an annotation file is given; a notebook that already holds the trained module draws each panel with `predict_and_draw(module, image, options, axes=ax)` and `draw_ground_truth(ax, targets, task)` instead, the skeleton for a pose grid travelling in `RenderOptions.skeleton` so the four tasks share one call shape. Every public name the scripts published stays importable from them as a re-export, so `scripts/_tests/test_draw_predictions.py` keeps its command-level cases and the drawing cases moved to `tests/viz/`, where the code they assert now lives.

**Ground truth is dashed, unfilled, and read by the training reader.** The new drawer, `draw_ground_truth(axes, targets, task)`, draws the label layer in the task's own geometry — boxes, instance rings, rotated quadrilaterals through the same `rboxes_to_polygons` the predicted rings use, boxes with a hollow ring at each visible point — and never fills or writes a score, so a prediction drawn solid on the same axes stays tellable from its target without a legend. What it takes is a `Targets`, which is what `CocoDetectionDataset` yields per image in the reading mode the task needs (`oriented` for `obb`, `keypoints` for `keypoints`); the file is not parsed a second time. The dataset needed two accessors for that — `file_names`, the companion of `image_ids` for a caller who arrives with a file rather than an id, and `targets_at(index)`, the precomputed targets without the image decode `__getitem__` performs — and both are the WP's one edit outside `_viz`, the scripts and the tests.

**Private, and matplotlib is a runtime dependency — because it already was.** The [WP-067](https://borda.github.io/lucid-YOLO/work_packages/wp-067/#wp-067) paragraph kept the drawers out of the package on the claim that `matplotlib` sits in the `dev` group and "a wheel a consumer installs pulls no plotting stack". Checked here rather than repeated: `pytorch-lightning[extra]`, in `[project].dependencies`, requires `matplotlib>3.1` (`importlib.metadata.requires("pytorch-lightning")` lists it under `extra == "extra"`), so every consumer install has pulled matplotlib since that extra was declared, and `torchmetrics` imports it the moment it finds it installed. The claim was false before this row and the row changes nothing about what a consumer receives. What it does change is the declaration: `matplotlib>=3.8` moves from the `dev` group to `[project].dependencies`, on the jsonargparse and tqdm precedent already in that list — a direct import is not a transitive dependency — and because [WP-168](https://borda.github.io/lucid-YOLO/work_packages/wp-168/)'s release guard reads declarations, not the transitive graph: `check_dependency_tiers` refused the tree with `_viz` importing a group-only distribution, and five `scripts/_tests/test_release_guard.py` cases (`test_happy_path_passes`, `test_main_without_tag_falls_back_to_head`, `test_metadata_only_leaves_gate_command_unrun`, `test_certifying_run_invokes_gate_exactly_once`, `test_metadata_only_verdict_refuses_to_call_tag_shippable`) failed on the live tree until it moved. The package is still `_viz`, underscore first, and the underscore is now an API contract rather than a dependency one: nothing else in `lucid_yolo` imports it, nothing outside it imports matplotlib, and the notebooks are its only callers, so its signatures can move with them. `tests/viz/test_import_surface.py` pins that from two sides. The dynamic side imports the shipped surface — `lucid_yolo`, `lucid_yolo.predict`, `lucid_yolo.eval.checkpoint`, `lucid_yolo.data` — in a fresh interpreter and asserts `lucid_yolo._viz` never entered `sys.modules`; the static side reads every shipped module's source and refuses an import line naming matplotlib or `_viz` outside the `_viz` subtree, which is the check that catches a function-local import no import of the surface executes. **No backend is selected in the package.** The plan had `_viz` keep the scripts' `matplotlib.use("Agg")` at module top. It does not: `use("Agg")` is a process-wide setting, and a notebook importing a package that makes it is switched away from its inline display — figures returned from a cell would stop rendering. So the backend selection stays in the two scripts and the two test conftests, which are the headless callers, and the package imports `pyplot` unconditionally with no `use()` before it. For the same reason `build_run_figure`, `plot_curves`, `predict_and_draw` and `show_predictions` return their figure open: the script saves and closes, a notebook displays, and closing inside the package would serve the first by breaking the second. The `svg.hashsalt` moved with the backend line, since it is the committed figure's concern and the same kind of global.



## WP-192 — the complete oriented evaluator uses the worker policy it already had

<a id="wp-192"></a>

**Timing evidence is host-specific and non-gated.** The off-repository procedures were profiling the public scoring loop, comparing five-run medians with `channels_last`, traversing the loader, and calling public `run`; the warm-up and repetition procedure is recorded below where available. The benchmark harness and raw output are not committed.

**The standalone path predates the image-size target and inherited-validation guard.** The evaluator's explicit `num_workers=0` arrived in `0fe08f4` on 12 August. The free-`/dev/shm` cap on automatic workers was already present from `9f1fa80` on 2 August; the image-size validation worker target (`9d0fa88`) and inherited-validation guard (`d09ded9`) arrived on 13 August, one day after the call site. `00af9e4` on 6 September renamed `_val_worker_cap` to `_val_worker_target` and clarified its documentation without changing the policy. Nothing revisited the call site, so automatic worker selection could only govern datamodules whose callers left worker selection open. Through the inherited-validation guard, the evaluator's explicit zero was raised to one validation worker wherever `/dev/shm` exists. All measured "existing route" baselines below, including 0.850 s, 9.757 s and 13.104 s, therefore used one validation worker; the current low-startup route runs zero workers and is unmeasured. A profile of the public scoring loop over 117 real DOTA tiles spent 3.60 of 5.10 s waiting for the loader. The rotated accumulator took 0.051 s, so even removing it entirely could save only 1.0% of that run. Converting the standalone module to `channels_last`, the other live candidate, moved the five-run median from 2.679 to 2.645 s and overlapped both ranges; it was rejected.

**Completeness is not itself the crossover.** Starting eight workers to score only eight tiles took a 1.784 s median against 0.850 s on the existing route. A positive `--limit` therefore keeps that route unconditionally — the measurement is the smallest size the diagnostic path runs at, not a sweep, so a large positive `--limit` keeps the same route by scope rather than by a remeasured crossover. With no limit, the evaluator asks the datamodule for its existing policy, then keeps it only when the loader has more batches than workers: otherwise no process can be reused after its first batch. That structural guard covers the measured one-batch regression and a complete but tiny custom split without introducing a dataset-size constant. No crossover measurement was taken on macOS / MPS, where workers spawn rather than fork, and the band of batch counts just above the worker count is also unmeasured. Nothing in the reader, letterbox, model, decoder, merge or metric changes. Tests walk `run` through both public branches and the tiny-complete fallback, while a separate real-pool case reads the same twelve tiles through one and two workers and compares images, boxes, labels, rotated boxes, difficult flags, order and the complete report.

**The loader result was repeated on an isolated CPU.** Five measured traversals after one warm-up on an `n2-standard-8` Ice Lake VM (Python 3.12.3, torch 2.14.1) moved from a 9.757 s median (9.651–9.987 s) with one validation worker to 2.658 s (2.609–2.781 s) with the policy's eight, a 72.96% median reduction. Every traversal yielded the same 117 tiles, 2,691 instances and tensor checksum. That figure is the loader alone: CPU-device inference was not measured. The policy's worker count derives from `os.cpu_count()`, which is blind to container CPU quotas and process affinity, so a host that limits either may start more workers than it can run. A quota- or affinity-aware count would change the datamodule policy that training shares and belongs in its own work package, not in WP-192.

**The complete pipeline keeps the gain.** Five measured public `run` calls after one warm-up on an NVIDIA L4 (driver 580.178.04, torch 2.14.1+cu130, batch 8) included loading, model inference, rotated decoding and scoring, whole-image merge and scoring, and report construction. The existing route took a 13.104 s median (12.909–13.253 s); the policy route took 7.830 s (7.336–8.090 s), a 39.66% median paired reduction. Each pair used the same freshly initialised oriented nano model over the same official-DOTA-derived 117-tile slice; metrics and report payloads were equal in these runs after removing the recorded seconds and the intentionally different worker-count diagnostic. The in-repository, gated CPU evidence of report equivalence is `tests/eval/test_eval_obb.py::test_run_through_real_workers_matches_run_through_low_startup_route`, which compares a real worker pool with the zero-worker route after removing those same fields; it does not establish CUDA determinism.

**The report now says which count ran.** A complete run's worker count is no longer the fixed `0` the report used to imply; it is whatever the datamodule's shared-memory- and image-size-aware policy picked on the host that ran it. `SplitScoring` and the JSON report's `info.workers` field now carry that count, read off the same loader `score_split` already builds, so a report is self-describing about which route scored it without reaching into the datamodule's private state. A failure of the policy route's worker pool itself, such as a worker that dies mid-pass and surfaces as the loader's `RuntimeError`, is not one of the pairing `ValueError`s `run` turns into a `FAIL:` line: it reaches the terminal as a traceback, `lucid-eval` exits with status 1, and no report is written.

**That field is an additive schema change, and its consumers were checked.** A repository-wide search over `tests/`, `notebooks/`, `docs/` and `src/` found no oriented-report golden and no consumer comparing the whole payload or the exact `info` key set. The tests and the other task reports read named keys, while `demo_obb.py` and the documentation only produce or name `obb_report.json`. The regression therefore pins the new field directly; downstream code that selects existing keys is unchanged, while a consumer enforcing an undocumented closed schema would need to accept the additive key.

**The floor moved to its exact live count, not a one-row nudge.** `_WP_FLOOR` only tracks additions correctly when it is raised to the roadmap's exact live count — the same ratchet rule [WP-152b](https://borda.github.io/lucid-YOLO/work_packages/wp-152b/) and [WP-165b](https://borda.github.io/lucid-YOLO/work_packages/wp-165b/) record, and the one `_ASSUMPTION_FLOOR` was caught violating at 47 rows of slack. ## WP-193 — post-backward state updates use fewer CUDA launches

<a id="wp-193"></a>

**The measured target is the complete interval, not either helper.** A public COCO val2017 training harness measured from one completed batch to the next, including loader wait, host-to-device transfer, forward and loss, backward, clipping, MuSGD, EMA and synchronization. **Two launch-bound stages make one post-backward change.** The existing optimizer already groups exact-shape CUDA matrices, but the `torch.vmap` layer around the scalar Newton--Schulz expression remains; it already lowered each product to one batched multiply, so the change drops that layer and folds the scale-and-add into the product epilogue. `_orthogonalize_batched` uses `baddbmm` for the same `b*A + c*A@A` and `a*X + polynomial@X` expressions, preserving each slice's normalization, coefficient triple, requested step count, gains, scaling and decay. Singletons and non-CUDA optimizer paths remain scalar. Both transformations are scheduling changes derived from this tree's buckets and profiler counts; no training constant or imported implementation enters the diff.

**Floating-point schedules are equivalent, not bit-identical.** Native batching and interpolation reassociate operations, so the regression contract is a bounded trajectory against the prior scalar formulas rather than byte identity. The repository's multi-step trajectory tests run on CPU, over three (6, 4) float32 matrices for the optimizer and float32 parameters for the EMA. The 40-step fixed-gradient CUDA run on an L4 is a one-off measurement, not a repository test, and no multi-step trajectory test covers square, wide or tall shapes or a float64 bucket. A finite one-step public-COCO run starts from the same loss and checks model and momentum differences directly. This row does not claim an unchanged long-run stochastic trajectory: tiny per-step differences can change later discrete assignments, as the repository already records for the exact-shape batching it replaces.

## WP-193b — compatible matrix batches and momentum dispatch

<a id="wp-193b"></a>

**Compatible matrix batches and momentum dispatch.** One diagnostic session after the native-batch and image-cache changes attributed a 49.28 ms median to the optimizer within a 159.60 ms complete detection interval on an isolated L4. Its 10.90 ms momentum-dispatch median suggested a 6.8% stage share; this is an exploratory opportunity estimate, not an independently repeated speedup or a universal ceiling. A single bounded-padding-only complete-path screen suggested 5.94%, without a run-level range; it did not establish a standalone improvement above the investigation's 8% bar. The combined candidate targets the remaining launch overhead within the same optimizer phase.

**Zero extension changes the batch, not the quintic.** For a wide matrix `X`, appending zero columns preserves its Frobenius norm and `X @ X.T`; every iterate of the existing polynomial therefore keeps those columns zero. CUDA matrices sharing the smaller dimension can run in one native batch, then crop and transpose back before their original dimension-dependent scale, gains and decay. Each padded gradient stack is bounded by the parameter and gradient bytes of the matrices in its own batch. A singleton, or a batch whose matrices all share one shape, keeps the exact-shape update; equal-shape matrices that share a smaller dimension with a matrix of another width join the padded batch. Parameters whose memory ranges overlap keep exact-shape keys, whichever storage object wraps them. No coefficient, iteration count or normalization rule changes.

**Momentum keeps its rounded operations.** Three foreach operations replace the CUDA per-parameter multiply, add and Nesterov add, with the original operation order. Device and dtype buckets keep independent state. Shared parameter/gradient/buffer storage and unusual restored state use the original scalar method; CPU and MPS keep their previous implementation. No public flag or checkpoint field is added.

**The numerical contract is bounded agreement.** Mixed-width GEMMs and reductions may round differently. A real one-step COCO run and its baseline-against-itself control have the same loss bytes, all 369 momentum buffers match bit for bit, and the largest model/buffer difference is 2.98e-8. A 60-step zero-warmup screen diverges in its BF16 trajectory, so this is not a claim of identical stochastic training or final accuracy. The mixed-shape scalar-oracle, storage-budget, alias, DLPack-overlap, dtype, checkpoint-resume and foreach recurrence tests cover the altered scheduling. The full accelerator goldens and long-run accuracy remain unverified; the existing [WP-193](https://borda.github.io/lucid-YOLO/work_packages/wp-193/) status stays open.

**The padding region is measured, not universal.** A five-repeat optimizer-only crossover screen found the unguarded x scale slower: 111.26 to 119.37 ms per step on the L4. Padding is therefore restricted to a smaller dimension of at most 256, the largest present in the measured nano workload; larger matrices retain exact-shape batches. The guarded screen improved the optimizer in all five scales, but those stage numbers are not the training claim. Parameter subclasses may legitimately refuse storage inspection: a baseline-compatible vector subclass exposed that regression before handoff. Such groups now keep their original keys and scalar momentum, including mixed groups where opaque storage may alias an ordinary parameter.

**The final claim includes the complete short fit.** Five alternating paired `Trainer.fit` runs on an isolated NVIDIA L4 (driver 580.178.04, torch 2.9.1+cu129, Python 3.11.17), after two discarded warm-up fits, used detection n, batch 4, 640 px, BF16 and four workers over 256 real COCO val2017 images. ## WP-193c — replay the network, keep the dynamic objective eager

<a id="wp-193c"></a>

**The source is the current training loop and R43's general-purpose API.** This follow-up was profiled from `01b4d4c` after compatible MuSGD batching merged, then rebased and remeasured on `50c2092` after the augmentation contribution merged. It changes how existing network work is dispatched, without rewriting any model, assignment, loss or optimizer arithmetic. `capture_network=False` is the default. Unlike the Inductor objective option, the recording contains only the detection network's forward and backward work; targets, loss, schedules, optimizer and EMA remain eager. Unlike the orthogonalization replay ([WP-197b](https://borda.github.io/lucid-YOLO/work_packages/wp-197b/), already on main), it records no optimizer work.

**One fit owns one recording.** A private tensor-tuple view composes the same backbone, neck and head. PyTorch supplies the autograd bridge. Recording restores RNG and all buffers after warmup, and mixed precision disables the autocast cache. A partial batch stays eager. Changed storage, modes, hooks or precision retire the recording. Public forward, validation and prediction remain ordinary calls. The holder registers no parameters and serializes no CUDA state; fit completion and exceptions clear it. CUDA single-device automatic optimisation and detection are the measured scope; higher-order differentiation and `compile_step` are excluded.

**BF16 has a measured runtime boundary.** FP32 and FP16 replay pass the exact eager comparisons on torch 2.4.1. BF16 does not, so BF16 replay starts at the verified 2.9 runtime and older BF16 fits remain eager. This avoids choosing a tolerance to hide the failed exact oracle; it does not claim that every intervening release was tested.

**Accumulation retains its own gradients.** The CUDA recorder reuses backward gradient storage. If a later backward must add to live gradients, the holder first clones those values out of that storage. This also covers custom optimiser or zero-grad hooks. An analytic scalar probe and independent eager-network regressions expose the unprotected alias: two microbatches can otherwise produce 6 where the derivative is 4. Ordinary one-step optimisation keeps the uncopied route.

**The claim is the complete short fit.** Five alternating paired, fresh-process `Trainer.fit` runs after two discarded warm-up fits used detection n (depth 0.50, width 0.25, max channels 1024), batch 4, 640 px, BF16 mixed precision, four workers, persistent workers and decoded-image caching on 256 real COCO val2017 images. The validation images are a 32-image subset of the training subset: this is throughput and trajectory evidence, never held-out accuracy. Persistent workers retain their augmentation state, so the mosaic-close callback is not evidence that worker-side mosaic actually closed.

On an isolated NVIDIA L4, driver 580.178.04, torch 2.9.1+cu129, Lightning 2.6.6, Python 3.12.3, synchronized fit time fell from median **92.589 s** (91.614-93.691) to **77.330 s** (76.234-78.265): **16.48%** by the ratio of medians. Recording setup is inside each fit; imports and model construction are outside both arms. Baseline-against-itself and every paired arm produced identical SHA256 digests over the raw tensor bytes of losses, model, optimizer, scheduler, EMA and metrics. This certifies those deterministic short trajectories, not all precisions, devices or long-run accuracy.

**Memory has two directions.** Median peak allocated memory fell from 828.5 MiB (822.0-831.4) to 711.3 MiB (711.3-711.3), while median peak reserved memory rose from 1022.0 MiB (1022.0-1038.0) to 1260.0 MiB (1260.0-1262.0). The graph pool is a cost of the opt-in path; no avoided-OOM or batch-capacity improvement is claimed. Fit callbacks drop the holder's recording, rather than promising that every outstanding autograd reference or allocator reservation vanishes immediately.

**The speed claim is limited to this small-batch workload.** Batch-32 screens changed direction relative to the batch-4 result, so the gain above is not a general claim; the shipped detection recipes train at batch 16, which was not measured here.

**Validation remains explicitly bounded.** Full `make gate`, accelerator goldens and final accuracy have not been run; this row stays open on those checks. Focused regression tests and timing logs are retained with the contribution's review evidence.
