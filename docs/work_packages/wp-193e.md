## WP-193e — preserve prediction gradient boundaries while replaying their work

<a id="wp-193e"></a>

A CUDA training trace on an L4 attributes 197.112 ms of four instrumented steps' host dispatch to the detection head's forward calls and 177.742 ms to its matching backward nodes, identified by their forward autograd sequence numbers. Together they occupy 28.40% of that 1.320 s host interval, before the separate prototype and semantic predictions. This diagnostic budgets submission work; complete-fit performance is measured separately below.

The opt-in `capture_segment_heads` records existing prediction calls through R43's graphed-callable API. Box/class stems retain independent input-gradient contributions. Each branch's coefficient routine, ProtoNet and the semantic predictor keep separate backward nodes, so an unused mask prediction leaves its parameters' gradients absent. The native per-level order, flattening, concatenations, tanh and prediction expressions remain unchanged. Backbone, neck, prototype fusion, assignment, losses, optimizer, schedules and EMA retain their existing execution.

Combining each branch's box/class predictions failed an exact state comparison, so the implementation retains separate stem contributions. FP32 replay also failed the semantic-bias gradient byte oracle. Replay is verified only for BF16 mixed precision on PyTorch 2.9 or newer; FP32 and FP16 retain native calls.

One fresh topology traversal feeds the guard checks. An attribute certificate retains bindings and checks mutable registry names and sequence elements, while current tensor storage, hooks, modes, precision and class dispatch remain independently checked. Changed or custom prediction stages, frozen prediction parameters, aliasing, logical negative/conjugate tensor views and unsupported runtime conditions use the native route. The native fusion is included in this guard without being recorded. Each prediction group retains one recorded input signature; a partial batch stays native. Transient holders keep original checkpoint keys and discard recordings on copying and at fit completion or failure.

Five alternating fresh-process pairs per isolated NVIDIA L4 host reduced complete nano segmentation fit time by 16.42% on g2-standard-8 and 11.01% on g2-standard-4. Native/replay medians (ranges), seconds:

| Host | Native | Replay | Time reduction |
| -- | -- | -- | -- |
| g2-standard-8 | 200.458 (199.715–201.380) | 167.549 (167.183–168.089) | 16.42% |
| g2-standard-4 | 230.050 (228.765–231.985) | 204.725 (203.420–205.093) | 11.01% |

Each fit uses 384 training and 32 disjoint validation COCO val2017 images with the original 80-class annotations, 10 epochs, batch 4, 640 px and BF16 mixed precision. Both arms enable prepared caching, device HSV, epoch prefetch, orthogonalization replay and update replay. The timer includes construction, cache preparation, graph recording, training, EMA, validation and checkpoints. Driver 580.178.04, torch 2.9.1+cu129, Lightning 2.6.6. Whole-process median time, including imports and verification, falls 15.94% on the standard host. The two allocations are separate environments; this is an observed configuration comparison, without a causal claim about CPU count alone.

All per-step-loss, model, optimizer, scheduler and EMA byte hashes and validation metrics match within all ten pairs and across the two hosts. An untimed ten-epoch pair also matches all eight dense prediction tensors at steps 0, 480 and 959 and matches the timed final state hashes. Final runtime source SHA256: `a747e080fe3ac8ea0103263c4dde6447779d54e6233679c3aab82c5ef687f7ee`. The actual reviewed test file passes 56 cases on the standard L4 with torch 2.9.1 and reports 48 passed / 8 skipped on torch 2.4. The tests cover recording activation, raw outputs and gradients, unused masks, partial batches, failure restoration and retirement warnings. Full pre-commit and focused CPU compatibility pass. Full `make gate`, accelerator goldens and long-run accuracy remain unverified.

A `_RecordedGroup`'s warmup shares the sibling network recorder's own hazard: a failed `make_graphed_callables` call can leave BatchNorm running-stat writes queued on its warmup stream, so the restore on the current stream must wait for a real synchronize first (`test_network_capture_guards.py::TestFailedRecording::test_synchronizes_before_buffer_restore` covers this for [WP-193c](../work_packages/wp-193c.md)). That case had no counterpart here; a new `tests/ptl/test_segment_head_capture.py::test_recorded_group_synchronizes_before_buffer_restore` injects the same failure into a real box stem's warmup on a local RTX 4060, asserts the device is synchronized before the BatchNorm buffer is restored, and confirms the failure still raises. Reverting the synchronize call in `_RecordedGroup.__init__` makes it fail, so it is not vacuous. This is a local compatibility check, not a timed claim.

`_SegmentHeadCapture.retire()` shares `_NetworkCapture.retire()`'s disabled-guard contract too: only the first incompatibility of a fit warns, so a second cause in the same fit must stay silent (`test_network_capture_guards.py::TestRetireWarning::test_later_cause_stays_silent` covers this for [WP-193c](../work_packages/wp-193c.md)). A new `tests/ptl/test_segment_head_capture.py::test_later_retire_cause_stays_silent` calls `retire()` twice on a bare holder and confirms only the first call warns; reverting the `if self.disabled: return` guard makes it fail.

Two CPU-only adapter-call tests also distinguish active replay from a silent native fallback while retaining recordings. With an unchanged signature and no pending backward, the graphed callable must run; while a backward is pending, the native callable must run. The replay case fails under an always-native guard mutation.

Peak CUDA reserved memory medians are 6084→6476 MiB on the standard host and 6084→6476 MiB on the supporting host. Graph pools cost memory, and the result is specific to the measured small-batch workload. A batch-16 screen is retained with the raw evidence without claiming a repeated large-batch benefit. The implementation keeps first-order automatic optimization on one CUDA device without accumulation; unsupported modes remain native.

Provenance: R43, this repository's native prediction calls and its own CUDA measurements; R12 supplies the public COCO data. No method arithmetic, coefficient, iteration count or method default changes. A15, A17 and A38 remain unchanged.
