# `notebooks/`

Runnable walk-throughs, committed as Python and published as notebooks (WP-188, D25). Every file here is a jupytext percent-format script: a plain `.py` that ruff lints and `git diff` reads, that `make gate` converts and executes through a kernel, and that `make notebooks` converts to the `.ipynb` the documentation site renders and the Colab badge opens. The `.ipynb` is a build product. It is never committed, and the `no-ipynb-tracked` pre-commit hook refuses one that reaches the index by force.

## Layout

```text
notebooks/                 committed sources, one <name>.py per notebook, plus this file
docs/notebooks/            GENERATED by `make notebooks`, gitignored: <name>.ipynb per source
```

The directory sits at the repository root rather than under `docs/` because every `^docs/` hook — `docs-present`, `docs-site`, the mkdocs-dialect mdformat — would fire on a `.py` there, and MkDocs would copy it into the site as a static asset.

## The percent format

A cell is a `# %%` line; a prose cell is `# %% [markdown]` with the markdown as `#`-prefixed lines below it. Every source opens with the SPDX header the `license-headers` hook requires of every `.py` in this repository, then a title cell carrying the Colab badge, then a bootstrap cell, then the walk-through:

```python
# SPDX-License-Identifier: Apache-2.0
# %% [markdown]
# # Development gates
#
# [![Open in Colab](https://colab.research.google.com/assets/colab-badge.svg)](https://colab.research.google.com/github/Borda/lucid-YOLO/blob/gh-pages/notebooks/<name>.ipynb)

# %%
import os
import sys

FAST = os.environ.get("LUCID_NOTEBOOK_FAST") == "1"
if "google.colab" in sys.modules:
    # !git clone --depth=1 https://github.com/Borda/lucid-YOLO
    # %pip install -e lucid-YOLO
    os.chdir("lucid-YOLO")
    sys.path.insert(0, "src")
```

Two things about that bootstrap are deliberate. It is guarded on `google.colab` being imported, so a run from a checkout — which is what the smoke test and any local reader do — skips it. And the clone and the install are shell lines, not `subprocess` calls: in the notebook they are `!git clone ...` and `%pip install ...`, and jupytext writes them into the `.py` as `# !git clone ...` and `# %pip install ...`, which is why the `.py` stays a file ruff can parse. The block still needs a real statement after them — `os.chdir` and the `sys.path` insert are that — because a guarded block of comments alone is a `SyntaxError` to any Python parser, ruff included.

## The demos call the library

Every step a demo notebook takes — download, fit, validate, predict, draw — is a call into `lucid_yolo` on an object the kernel holds: `download_coco` or `build_tiles` for the data, `DetectionLitModule` and `DetectionDataModule` built from the values the tier's `*_nano_smoke.yaml` carries (each one named in the prose beside it, the YAML file cited), a `pytorch_lightning.Trainer` for `fit` and `validate`, `lucid_yolo.predict` and `lucid_yolo._viz` for the answer and the picture. The command the documentation spells is quoted as prose — "the same run from the shell" — never executed: no `lucid_yolo.cli` import, no `DetectionCLI`, no `subprocess`, no `%%bash` cell, no checkpoint reload. The module that trained is the module that predicts.

```python
# %%
spec = scale_spec("n")
model = DetectionLitModule(spec.depth, spec.width, spec.max_channels, num_classes=NUM_CLASSES, task="detect", lr=0.01, warmup_epochs=1, ...)
dm = DetectionDataModule(DATA_ROOT, batch_size=4 if FAST else 64, num_workers=0 if FAST else 8, variant="n", img_size=128 if FAST else 640, ...)
trainer = Trainer(max_epochs=1, accelerator="cpu", limit_train_batches=8, ...) if FAST else Trainer(max_epochs=2, precision="16-mixed", ...)
trainer.fit(model, datamodule=dm)
```

Three things follow from every value being a Python value:

- **`FAST` decides in Python, at the call.** The fast budget is a conditional argument — `batch_size=4 if FAST else 64` — not a string of flags handed to another process, and the branch sits beside the value it changes.
- **What the CLI links, the notebook states.** `lucid-yolo fit` expands `variant` onto the module's `depth`/`width`/`max_channels` and the data module's policy, links `model.task` onto `mask_targets`/`rotated_targets`/`keypoint_targets`, and installs the TensorBoard-plus-CSV logger pair; a notebook passes each of those itself, and says so.
- **The last expression of a figure cell is the figure**, spelled `None if FAST else prediction_grid(640)` — a bare name is `B018` to ruff, and the `if` is the no-figure clause of the fast contract.

The two bootstrap lines are the only IPython in the file.

Imports may sit in the cell that first needs them rather than at the top of the file; `E402` is the one ruff rule `pyproject.toml` relaxes for `notebooks/**`, and the only one until a real notebook needs another.

## The fast contract

Every notebook reads one variable, once, at the top:

```python
FAST = os.environ.get("LUCID_NOTEBOOK_FAST") == "1"
```

With `LUCID_NOTEBOOK_FAST=1` the notebook must cap itself so the whole file runs on CPU in well under a minute, with nothing on disk it did not generate:

- **the dataset is the synthetic slice** — `fuse_augmentations.data.generate_dataset` the way `scripts/overfit_micro.py` uses it, or the YOLO-format root `tests/fixtures/synthetic.py` writes (A26); a notebook that walks COCO or DOTA in its full run never touches either under `FAST`;
- **one epoch** (`max_epochs=1`, or `fast_dev_run=True`), a small batch, a handful of images;
- **no figures** — nothing calls into matplotlib's rendering;
- **no downloads** — no checkpoint, no archive, no network at all.

Without the variable the notebook does whatever it is for: the real dataset, the real epoch count, the figure, the checkpoint. Fast proves the code path still exists; full proves the number the prose claims; the Colab run proves the badge.

## The badge

The title cell of every source carries this link, with `<name>` the source's stem:

```markdown
[![Open in Colab](https://colab.research.google.com/assets/colab-badge.svg)](https://colab.research.google.com/github/Borda/lucid-YOLO/blob/gh-pages/notebooks/<name>.ipynb)
```

It points at the `gh-pages` **branch**, not at `main`: `main` carries no `.ipynb` by design, so the `Docs` workflow converts the sources on every push to `main`, copies each `.ipynb` to `site/notebooks/`, and `ghp-import` commits the built site onto `gh-pages` — one branch carrying the site and the notebooks, read by Pages and by Colab's GitHub loader alike. Until the first push after a notebook lands, its badge is dead by construction — the page renders, the link 404s. The site's "edit this page" link on a notebook page has the same shape: it points at `docs/notebooks/<name>.ipynb` on `main`, which does not exist; the file to edit is `notebooks/<name>.py`.

## Building and checking

```bash
make notebooks   # notebooks/*.py -> docs/notebooks/*.ipynb (no-op with no sources)
make docs        # runs `notebooks` first, then the strict site build
make test        # the fast case of every notebook, with the rest of the offline suite
make test-gpu    # the full case, marked gpu + data, with the rest of the accelerator half
```

Three layers, each answering a question the others cannot:

| Layer | Runs where | Proves |
| -- | -- | -- |
| **fast** — `LUCID_NOTEBOOK_FAST=1`, CPU, `MPLBACKEND=Agg`, no marks | `tests/notebooks/test_notebooks_run.py` under `make test`, so under `make gate` and on every commit | the code the notebook walks still exists and still runs |
| **full** — same command, no variable, marked `gpu` and `data` | the same file under `make test-gpu`, so the nightly `gate-gpu.yml` | the run the prose describes still produces what the prose claims |
| **Colab** — click the badge | a person, once per notebook work package | the published `.ipynb` opens and runs end to end on a GPU that is not this machine's |

The smoke test does not run the `.py` as a script — it could, since the demos are library calls, but a script run reads the bootstrap's `# !git clone` and `# %pip install` as the comments they are and proves nothing about the two lines a Colab reader depends on. Instead it runs `jupytext --from py:percent --to ipynb --execute --set-kernel python3 --run-path <repo root>` on each source: the conversion `make notebooks` performs, plus execution through a Jupyter kernel, so the notebook runs as it runs for a reader, magics included. The kernel is the test's own interpreter with no install step: `python3` is the kernelspec `ipykernel`'s wheel drops into `.venv/share/jupyter/kernels/`, its `argv[0]` is the bare word `python`, and `jupyter_client` swaps that for the `sys.executable` of whoever launches the kernel — the venv's Python, because pytest runs jupytext as `python -m jupytext`. (`--set-kernel -`, jupytext's own "current interpreter" spelling, rejects that spec: it compares `argv[0]` to `sys.executable` as files, and `python` is not one.) `--from py:percent` is what keeps the bootstrap lines magics: left to guess, jupytext reads the indented `# !git clone` in the Colab block as an unescaped magic and picks its `hydrogen` format, which never uncomments a magic; `make notebooks` and `docs.yml` pass the same flag for the same reason. The fast case has to finish within the ceiling the test sets, kernel start included — a kernel starts in about two seconds, and on an Apple-silicon CPU the four demos measured about 11 s each and the development gates 26 s.

The site itself proves nothing about execution: `mkdocs-jupyter` renders the converted file with `execute: false`, so what the page shows is the source cells and the badge, never an output. That is the point — docs CI stays torch-free, and a notebook that rots fails in the suite rather than in a page.

## Adding one

1. Write `notebooks/<name>.py` in the shape above — header, title cell with the badge, bootstrap, `FAST` read once, then the cells, every step a library call on an object the kernel holds, the fast budget a conditional argument.
2. Add `- <Title>: notebooks/<name>.ipynb` under the `Notebooks` nav section in `mkdocs.yml` (uncommenting the section for the first one). The `docs-site` hook fails a source with no entry, and `mkdocs build --strict` fails an entry with no source.
3. `make notebooks && make docs`, then `make gate`: the fast case has to pass on CPU within the ceiling `tests/notebooks/test_notebooks_run.py` sets.
4. After the push to `main`, open the badge. That is the human check, and the work package is not done until it has been made.

Never commit the `.ipynb`. `docs/notebooks/` is gitignored, and the hook exists for the `git add -f` that ignores that.
